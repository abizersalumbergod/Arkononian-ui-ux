# Delivery orchestration

How to carry a spec or a ticket set to done: building a ticket test-first, running a task graph on one integration branch, charting a huge effort as a map of decision tickets, triaging an issue tracker when one is in scope, keeping memory across long efforts, and handing the steps only a human can perform to a staged procedure.

**Load when:** building from a spec or tickets, an effort is too big for one session, several independent pieces could run at once, an issue tracker is in scope, a goal runs over many sessions, or a step needs a human (provisioning, credentials, DNS, a third-party dashboard, a cutover). **Owns:** implementing a ticket, the task graph and integration branch, the decision map (wayfinding), triage roles, project memory for long efforts, and the staged procedure for human-only steps.
**Related:** [interview-and-specs](interview-and-specs.md), [test-driven-development](test-driven-development.md), [review-and-handoff](review-and-handoff.md), [repo-guardrails](repo-guardrails.md), [codebase-design](codebase-design.md), [prototyping](prototyping.md), [domain-model](domain-model.md), [security-and-privacy](security-and-privacy.md), [quality-gates](quality-gates.md)

## Decision rules

1. **Implement one ticket at a time, test-first at the agreed seams.** State the ticket's title before starting; if the reference is ambiguous, ask. Typecheck regularly, run single test files regularly, run the full suite once at the end ([test-driven-development](test-driven-development.md)), then review the work ([review-and-handoff](review-and-handoff.md)).
2. **Commit only when the user asks for commits.** Otherwise leave the work in the working tree and say so. Never push, open a pull request or tag a release unasked: those publish ([SKILL.md §1](../SKILL.md)).
3. **Tickets form a task graph.** Blocking edges mean the work is not a list of steps: at any moment there is a **frontier** of tickets whose blockers are all done. Work the frontier; recompute it after every completion.
4. **One integration branch per spec.** Each ticket is built in its own isolated workspace branched from it, merged back when done, and the branch tip is merged into the ticket branch before the ticket reports done. Review the whole integration branch once all tickets are complete and fix the findings in one fresh pass.
5. **Isolated workers, when the host offers them.** Give each ticket a worker with a fresh context, run independent ones in the background for concurrency, and keep communication sparse: pass **context pointers** (paths to the spec, tickets, research notes, commits) and do not duplicate what a pointer already holds. Without workers, run the frontier sequentially, one ticket at a time, starting each from the pointers rather than from memory.
6. **Exploration is separate work.** A worker may gather the codebase or documentation facts the tickets need and save notes outside the repository, so implementers spend their context on building.
7. **Plan, do not charge.** For a huge effort wrapped in fog, chart the way before building: a map of decision tickets, resolved one at a time until the route is clear. The pull to just do the work usually signals the edge of the map and the time to hand off.
8. **Name, do not number.** In everything a human reads, refer to a map or ticket by its title; a wall of identifiers is illegible.
9. **A map is an index, not a store.** A decision lives in one place, its ticket; the map gists it and points to it.
10. **Claim before work.** Mark a ticket as yours before starting so concurrent sessions skip it; never resolve more than one ticket per session, except research tickets.
11. **Human decisions need the human.** A decision ticket worked "with a human" resolves only through a live exchange; never answer your own questions on their behalf.
12. **Triage writes are external actions.** Applying labels, commenting, closing or opening issues and pull requests on a tracker needs approval naming the action and destination ([SKILL.md §1](../SKILL.md)); every comment posted for triage starts with a line saying it was generated by AI.
13. **Write history, not the present.** Project memory for long efforts is a folder of interlinked, dated notes. Date every claim; cite the commit a claim about code was true at; never write "currently" or "now" about code without a date or commit; when something changes, add a new dated claim and mark the old one superseded.
14. **Think on two tracks.** Tactical (finish this task) and strategic (change the environment so the next task goes better): constrain APIs and functions, add checks that force correctness, give agents the data they need (dev-server logs, a test database, a browser), and allow no one-off workarounds that bypass the process.
15. **A human-only step gets a staged procedure.** Scope every manual step and every value captured; give the exact path for each stage; never invent interface steps you cannot verify; confirm before anything irreversible; take secrets through hidden entry; do not run the procedure yourself.

## Specifications

### Task-graph loop

| Step | Action |
|---|---|
| 1 | Read the spec and tickets; build the graph and list the frontier |
| 2 | (Optional) one exploration pass saving notes outside the repository |
| 3 | Create the integration branch (only if branches are in scope for this user) |
| 4 | For each frontier ticket: an isolated workspace from the integration branch, test-first build, merge the branch tip into it, report done |
| 5 | Merge each finished ticket into the integration branch |
| 6 | Recompute the frontier; start newly unblocked tickets |
| 7 | When all are done: review the integration branch, fix findings in one pass |
| 8 | Close tickets the way the project's tracker or files do; report the branch; remove temporary workspaces |

### Decision map (for work too big for one session)

Files in a folder such as `.scratch/<effort>/`, or issues on a tracker the user approved:

```md
## Destination
What reaching the end of this map looks like (the spec, decision or change). One or two lines; every session orients to it first.

## Notes
Domain, standing preferences, which modules of this package to consult.

## Decisions so far
- [<closed ticket title>](<pointer>): one-line gist of the answer

## Not yet specified
In-scope fog you cannot ticket yet; graduates as the frontier advances.

## Out of scope
Work ruled beyond the destination; closed, never graduates.
```

| Ticket type | Who | Used for |
|---|---|---|
| Research | Agent alone | Reading documentation, third-party interfaces or local resources to surface a fact a decision waits on |
| Prototype | With a human | A cheap, concrete artifact to react to when "how should it look or behave" is the question ([prototyping](prototyping.md)) |
| Grilling | With a human | A conversation; the default ([interview-and-specs](interview-and-specs.md), [domain-model](domain-model.md)) |
| Task | Human or agent | Manual work that must happen before a decision can be made (signing up for a service so its interface can be judged, provisioning access); the only type that does rather than decides |

A ticket is a question sized to one session. Fog is not ticketed: the test is whether you can state the question precisely now, not whether you can answer it now. Resolving a ticket records the answer as a resolution note, closes the ticket and adds a gist and pointer under Decisions so far; then graduate newly specifiable fog into tickets (create them, then wire blockers in a second pass with real identifiers) and rule anything beyond the destination out of scope instead of resolving it.

### Triage roles (when an issue tracker is in scope and the user asks)

| Kind | Roles |
|---|---|
| Category (exactly one) | `bug`, `enhancement` |
| State (exactly one) | `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix` |

An unlabeled item goes to `needs-triage`, then to one of the others; `needs-info` returns to `needs-triage` when the reporter replies. Show what needs attention in three buckets, oldest first: unlabeled, `needs-triage`, and `needs-info` with new activity. To triage one item: read it fully with prior notes; check redundancy (search the codebase by domain concept for an existing implementation) and prior rejection ([domain-model](domain-model.md)); recommend a category and state and wait; verify the claim (reproduce a bug from the reporter's steps, check that a PR does what it says); interview if it needs shaping; then apply the outcome: a durable agent brief for `ready-for-agent` ([interview-and-specs](interview-and-specs.md)), notes for `needs-info` (what is established; specific questions for the reporter), and for `wontfix` a pointer to where an existing feature lives, a polite explanation for a bug, or an out-of-scope record for an enhancement. A pull request is an issue with attached code and uses the same roles.

### Human-only procedure

For each stage write: the URL or place to open, what to do there, where a value appears, the variable it fills, whether it is secret (hidden entry) or public, and where it is written (an environment file, a CI secret, both, or nowhere). Order stages by dependency, one focused task each, and confirm before any irreversible action. A cross-platform script skeleton (Node, so it runs on Windows without a shell):

```js
// wizard.mjs: run with `node wizard.mjs`. Stages are authored below; the helpers stay as they are.
import { createInterface } from "node:readline/promises";
import { appendFileSync, readFileSync, existsSync, writeFileSync } from "node:fs";
import { spawn } from "node:child_process";

const say = (t) => console.log(t);
const ask = async (q) => { const rl = createInterface({ input: process.stdin, output: process.stdout }); const a = await rl.question(q); rl.close(); return a.trim(); };
const confirm = async (q) => /^y(es)?$/i.test(await ask(`${q} [y/N] `));
function askSecret(q) {
  return new Promise((resolve) => {
    process.stdout.write(q); let v = "";
    process.stdin.setRawMode?.(true); process.stdin.resume(); process.stdin.setEncoding("utf8");
    const onData = (c) => {
      if (c === "\r" || c === "\n") { process.stdin.setRawMode?.(false); process.stdin.pause(); process.stdin.off("data", onData); process.stdout.write("\n"); resolve(v); }
      else if (c === "\u0003") process.exit(130);
      else if (c === "\u007f" || c === "\b") v = v.slice(0, -1);
      else v += c;
    };
    process.stdin.on("data", onData);
  });
}
function openUrl(url) { // only open URLs authored in this file
  const [cmd, args] = process.platform === "win32" ? ["cmd", ["/c", "start", "", url]] : [process.platform === "darwin" ? "open" : "xdg-open", [url]];
  spawn(cmd, args, { stdio: "ignore", detached: true }).unref();
}
function writeEnv(key, value, file = ".env") { // idempotent upsert, never echoes the value
  const lines = existsSync(file) ? readFileSync(file, "utf8").split(/\r?\n/) : [];
  const i = lines.findIndex((l) => l.startsWith(`${key}=`));
  if (i >= 0) lines[i] = `${key}=${value}`; else lines.push(`${key}=${value}`);
  writeFileSync(file, lines.filter((l, n, a) => l !== "" || n < a.length - 1).join("\n") + "\n");
}

const stages = [
  { title: "Stage 1 of 1: <name>", run: async () => { /* openUrl(...); const v = await askSecret("..."); writeEnv("NAME", v); */ } },
];
for (const [n, s] of stages.entries()) { say(`\n${s.title} (${stages.length - n - 1} left after this)`); await s.run(); }
say("\nDone. Summary: <list what was written and where, never the values>.");
```

Check it statically (syntax check, every captured value lands where promised, every secret name matches a reference in the CI configuration) and hand it to the user to run; it opens browsers and waits for a person. A procedure is ephemeral by default; commit it only if the user wants a repeatable setup path.

### Project memory for long efforts

A folder of interlinked notes outside the code: an index listing every page with a one-line summary, one page per decision, recurring problem, subsystem or preference, and sources (issues, pull requests, transcripts, reports) cited, never copied. Three operations: ingest (update every page a new fact touches, and the index), query (read the index before a decision; file an answer worth keeping), lint (look for contradictions, orphan pages, missing links and claims newer sources overtook). For this package the glossary, decision records and the design decision records already play that role; use a notes folder only when they are not enough.

## Implementation

1. Read the spec or ticket set and decide the mode: single ticket (rules 1 and 2), task graph (rules 3 to 6), decision map (rules 7 to 11), or human-only step (rule 15).
2. For a graph: list the frontier, build each ticket with its own tests and its own review, merge, repeat; finish with one review of the whole branch ([review-and-handoff](review-and-handoff.md)).
3. For a map: name the destination first, chart breadth-first, create what is specifiable, leave the rest as fog, and stop; resolving comes in later sessions, one ticket each.
4. At the end of each session, record decisions and open questions as pointers, not prose copies ([review-and-handoff](review-and-handoff.md), handoff).

## Failure modes & fallbacks

| Failure | Fix / fallback |
|---|---|
| No isolated workers or branches in this host | Run the frontier sequentially in the working tree; keep one ticket per commit only if commits were requested |
| Two tickets touch the same files | They are not independent; add a blocking edge or merge them |
| A ticket stays red after three fixes | Stop; record the evidence, mark it blocked and ask ([troubleshooting](troubleshooting.md), rule 13) |
| The map's fog never clears | The destination is too wide; redraw it and move the excess to out of scope |
| A triage comment would be posted without approval | Draft it as a file and ask |
| A wizard step relies on an interface you cannot see | Say so, ask the user or check the vendor's documentation; never write guessed clicks |
| Memory notes contradict the repository | The repository wins; mark the note superseded with a date |

## Verification

- Each finished ticket shows red-then-green evidence, and the integration branch passed review before it was reported complete.
- No pull request, tag, push, tracker write or message was made without an approval naming it.
- A map's Decisions so far points to a resolved ticket for each line, and nothing past the destination remains open.
- A human-only procedure traces statically: every value lands where stated and every CI secret name matches its reference.
